# Thunder Database Schema & Code Sync Fix

## Issues Fixed

Your login API was throwing this error:
```
ERROR: column "address" does not exist (SQLSTATE 42703)
```

This was caused by several misalignments between the database schema, Go domain structs, repository queries, and service code.

## Changes Made

### 1. **Database Schema (schema.sql)**
- Added DROP statements to cleanly recreate tables in order of dependencies
- Ensured all columns are properly defined: `address JSONB`, `metadata JSONB`, `email VARCHAR`, etc.
- Removed conditional "IF NOT EXISTS" clauses for deterministic schema creation

### 2. **User Domain Struct (internal/user/domain.go)**
**Before:**
- `ID` was string
- Used `PinHash` instead of `PasswordHash`
- Used `Type` instead of `Role`
- Missing `UpdatedAt`, `Email` fields

**After:**
- `ID` is now `int64` (auto-generated by database)
- Renamed `PinHash` → `PasswordHash`
- Renamed `Type` → `Role`
- Added `Email` and `UpdatedAt` fields
- Added response types: `LoginResponse`, `AuthCheckResponse`, `AuthVerifyResponse`, `GetRoleResponse`

### 3. **Repository (internal/user/repository.go)**
- Updated all column selections to match the schema exactly
- Fixed field name mappings: `role` → `Role`, `password_hash` → `PasswordHash`
- Removed manual ID insertion (BIGSERIAL is auto-generated)
- Updated method signatures to use `int64` for user IDs
- Added `Email` and `UpdatedAt` to all SELECT and INSERT operations

### 4. **Service (internal/user/service.go)**
- Simplified service logic to match new domain structure
- Removed unused methods and simplified to core auth functionality
- Changed ID handling from UUID strings to int64
- Updated all references from `PinHash` to `PasswordHash` and `Type` to `Role`

### 5. **Handler (internal/user/handler.go)**
- Cleaned up duplicate methods
- Added proper ID parsing (string to int64)
- Implemented `GetRole` endpoint correctly
- Updated all response types to match new domain structs

### 6. **Auth Service (internal/pkg/auth/service.go)**
- Updated `Claims.UserID` from string to int64 to match database type

### 7. **Demo Data (demoData.sql)**
- Updated to use proper bcrypt hashes for passwords (1234, 5678, 9999, 4321)
- Separated `address` field from `metadata` JSONB object
- Removed obsolete timestamp specifications (auto-handled by DEFAULT CURRENT_TIMESTAMP)
- Cleaned up product demo data

## Setup Instructions

### Step 1: Run Schema Migration
Execute the fresh schema on your Neon database:
```bash
# You'll need to connect to your Neon database and run schema.sql
# Using your DATABASE_URL connection string:
psql $DATABASE_URL < schema.sql
```

### Step 2: Seed Demo Data
```bash
psql $DATABASE_URL < demoData.sql
```

### Step 3: Test Login
```bash
curl -X POST "http://localhost:8080/api/v1/auth/login" \
  -H "Content-Type: application/json" \
  -d '{
    "phone": "9876543210",
    "pin": "1234",
    "tenant_id": "factory-a"
  }'
```

Expected response:
```json
{
  "token": "<generated_token>",
  "user_type": "admin",
  "user_id": 1
}
```

## Database Schema

All tables now use:
- `id BIGSERIAL PRIMARY KEY` for users (auto-incrementing)
- `tenant_id VARCHAR(50)` with foreign key to tenants
- `password_hash VARCHAR(255)` for bcrypt hashes
- `role VARCHAR(20)` for user roles (not `type`)
- `address JSONB` separate from metadata
- Proper indexes for performance

## Verification

After setup, verify your database with:

```sql
SELECT 
    column_name,
    data_type,
    is_nullable
FROM information_schema.columns 
WHERE table_name='users'
ORDER BY ordinal_position;
```

Should show columns in this order:
1. id (bigint)
2. tenant_id (character varying)
3. name (character varying)
4. phone (character varying)
5. email (character varying)
6. password_hash (character varying)
7. role (character varying)
8. status (character varying)
9. metadata (jsonb)
10. address (jsonb)
11. created_at (timestamp with time zone)
12. updated_at (timestamp with time zone)

## Troubleshooting

If you still get column errors:
1. Ensure schema.sql was fully executed (including DROP statements)
2. Run `\d users` in psql to verify table structure
3. Check for any migration conflicts or partial executions
4. Verify DATABASE_URL is pointing to the correct database
